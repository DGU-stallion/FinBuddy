# 验证的边界：一个错 3 倍的数字如何穿过 9,000 行测试

> 一次 24 小时 AI 产品开发的复盘。写给招聘方，也写给下一个接手的人。
> 本文所有数字均可在仓库内复现；所有会话记录、真机数据、失败路径都保留在仓库里。

---

## 0. 摘要

我用 24 小时、配合 AI Coding，做了一个 A 股投资命题核验工具，交付时 **46 个测试文件 / 558 项测试全绿**、类型检查干净、Lint 零警告、生产构建通过。

它在演示时是能用的。三栏证据、可点击角标、确定性测算滑块都正常。

**但它的预置案例里，有一个数字错了 3 倍**——而且这个错误数字带着"口径：TTM"的正确标签，穿过了测试、契约校验、代码评审，渲染成一张看起来很精确的图表。

发现它的人不是测试，不是 AI，是**人看了一眼**。

本文记录三件事：
1. 这个错误为什么能穿过所有关卡（因为它们都在监听"报错"）
2. 我用 24 条缺陷记录做的一次量化分析：**83% 的缺陷能被系统发现，17% 结构性地不能**
3. 我从中学到的、且已经改变我工作方式的一条纪律

> 附注：本文第一版把上面比例写成「93% / 7%」。实际是 20/24 = 83.3%。
> 写错的原因和本文主题完全一致——**我凭感觉估了个数，没回去数**。
> 它是靠把 24 条记录重新逐条分类才发现的。**这个错误本身就是本文论点的例证**，故保留说明。

## 1. 那个数字

预置案例之一是宁德时代。系统给出的基准营收是 **11,128 亿元**。

问题在于：宁德时代一年的营业收入是三四千亿量级。**11,128 亿是它大约三年的营收。**

这个数字不是模型编的。它来自真实接口，被真实代码计算出来：

```ts
// lib/gateway.ts
income = await deps.fuyao('get_a_share_financials_income_statements', {
  thscode, period: 'quarterly', limit: 5,
});

// lib/financials.ts
const last4 = valid.slice(0, 4);
baseRevenue = last4.reduce((s, p) => s + p.operatingIncome, 0);  // ← 把 4 期直接相加
```

**根因**：扶摇接口的 `period: 'quarterly'` 返回的是**年内累计值（YTD）**，不是单季值。看起来是这样：

| 报告期 | 接口返回值 | 真实语义 |
|---|---|---|
| 2026Q2 | 2,769 亿 | 2026 上半年累计 |
| 2026Q1 | 1,291 亿 | 2026 一季度累计 |
| 2025Q4 | 4,237 亿 | 2025 全年 |
| 2025Q3 | 2,831 亿 | 2025 前三季累计 |

这四期直接相加 = 11,128 亿。而单年营收的正确读法只需取 `2025Q4 = 4,237 亿`（最近完整财年）。

**这个错误是可内部验证的**——不需要知道宁德时代的真实营收：

```
求和 11,128 亿 ÷ 最近完整财年 4,237 亿 = 2.63 倍
```

**一个公司不可能在一年里赚出 2.63 年的营收。** 任何一条量级检查都能当场拦下它。

## 2. 它穿过了什么

这是全文最该看的部分。错误的数字不是"漏网"——它拿到了全部通行证：

| 关卡 | 结果 | 为什么没拦住 |
|---|---|---|
| 单元测试（46 文件 / 558 项） | ✅ 全绿 | `sumTTM` 的单测用**合成数据**验证加法。加法确实没错 |
| 量级断言 | ✅ 通过 | 测试里写的期望值是 `1245 亿 × 10% × 35% × 85% ≈ 37 亿`——**它在验证乘法，输入错了照样通过** |
| 输出契约校验 | ✅ `ok: true` | 契约只检查三栏是否齐全、真空期是否声明、角标是否编造。**完全不看数字** |
| 角标溯源 | ✅ 全部命中 | 引用号确实是本轮工具真实返回的。**引用真实，数值错误** |
| 双轴代码评审 | ✅ 无违规 | 评审查的是"代码是否符合 ADR"和"是否符合票面"，不是"这个数字是否符合现实" |
| 参数守卫 | ✅ 通过 | `Number.isFinite(11128e8)` 返回 `true`。**这是个完全合法的有限数** |
| UI 标注 | ✅ **"口径：TTM"** | 标签是正确的。**所以它比没有标签更危险** |

最后一行的分量，要对照这个项目的题目要求来看：

> 题目原文：「核心结论必须能回到原始字段或原文，并**明确来源、时点、单位及统计口径**；
> 数据缺失、冲突、过期或调用失败时**不得静默生成"正常"结论**。」

我的系统**没有**静默生成"正常"结论。

**它生成了一个错误结论，并且盖上了章。**

推荐一条 TTM 口径、标注了数据时点、挂着可点击的存证角标。用户看到的不是"这里有可疑数据"，而是**"这是一个权威、可追溯、口径明确的数字"**。

## 3. 24 条缺陷的分布

这个项目在开发过程中记录并修复了 **24 个真实缺陷**（不是假想风险，是实际出现并修掉的）。我把它们的"发现渠道"做了统计：

```
10  ██████████  AI 双轴代码评审（Standards + Spec）
 4  ████        AI 主动追查
 3  ███        自动化测试
 3  ███        浏览器级脚本（Playwright/CDP）
─────────────────────────────────────────
 4  ████        ★ 人眼实测
```

**83%（20/24）的缺陷由系统自己发现。** 这个数字很漂亮——AI 评审、自动化测试、浏览器脚本构成了一个高效的缺陷发现机器。

> 精确分类（按 README 表格实际记录）：AI 双轴代码评审 10、AI 主动追查 4、
> 自动化测试 3、浏览器级脚本 3 → **系统侧 20**；人眼实测 4 → **人工侧 4**。合计 24。

但请看那 4 条是**什么**：

| # | 缺陷 | 本质 |
|---|---|---|
| 15 | `bg-slate-950/98` 被 Tailwind **静默丢弃** → 存证抽屉完全透明 | 不报错 |
| 16 | `.next` 被 dev 与 build **交叉污染** → CSS 404 | 不报错 |
| 17 | 提交闸门失效 → 点一次跑两轮 | 不报错 |
| 19 | 构建污染 `.next` → CSS/JS 全 404、页面裸文字 | 不报错 |

**四条全部是"不报错的失效"。** 这不是巧合，是**结构性**的：

- Tailwind 遇到不在档位内的 `/98`，**不报错**——它只是不生成那条样式。构建成功、Lint 干净、测试全绿。
- `next dev` 和 `next build` 共用 `.next/` 目录，互相污染后 webpack 出问题，**不报错**——只是某个请求变成 404。
- 页面拿不到 CSS，**不报错**——HTML 完整、JS 完整、`onClick` 都在，只是"不好看"。

而所有测试、所有监控、所有代码评审，**都在监听"报错"**。

> **一个不报错的失效，对一套监听报错的仪器来说，是完全透明的。**

这就是那 **17%** 为什么必须由人发现。**不是因为人更聪明，是因为人用的是另一套传感器**——眼睛看的是"这东西看起来对不对"，而不是"这东西退出码是几"。

## 4. 那 4 条是怎么被发现的（以及我如何连续两次归错因）

用户的第一句反馈很短：

> "我登录 localhost:3000 看了，**只有文字，没有 UI，也没有交互**。"

这句话直接推翻了我"558 项测试全绿"的自信。追下去是两个真实的静默失效（#15、#16）。

**但这还不是最值得记的部分。**

同一时期，用户报告了另一个现象：**"点一次预置问题，重复了两次。"**

我为此连续**两次归错了因**：

| 我当时的判断 | 我做了什么 | 结果 |
|---|---|---|
| ①"你连点了" | 加同步 `inFlight` ref 闸门 + 5 个连点用例 | 测试全绿，**问题依旧** |
| ②"中文输入法选词误提交" | 用 CDP 真实输入法复现，红→绿验证 | 修好了一条**独立存在的真缺陷**，**问题依旧** |

两次我都在**客户端的提交路径**里找原因。

真相是：**提交只发生了一次，HTTP 请求也只有一次——但它渲染出了两轮。**

真因在**服务端流的事件顺序**：

```ts
// 错误顺序
data-steps → data-plan → start   ❌  AI SDK 开出两条 assistant 消息
// 正确顺序
start → data-steps → data-plan   ✅  一条
```

一次请求 → 2 条 assistant 消息 → 同一提问渲染两轮。**与模型无关，每次必然复现。**

### 转折点是"停止推理，改成观测"

我前两次失败，是因为我在**猜机制**。第三次我做了一件不同的事：

```
抓下真实完整 SSE（1,799 个事件）
  → 原样回放给真实浏览器
  → 二分截断
  → 3 步定位到具体事件顺序
```

⚠️ 这里还有一个**差点骗过我自己**的插曲：我第一版回放脚本**没有复现**这个 bug，我一度以为自己又错了。真实原因是回放流里的 `start` 漏了 `messageId` 字段——**带上它才会触发，不带就不会**。

也就是说：**我的验证脚本一度是一把永远绿的假尺子。** 一个不会变红的测试，比一个失败的测试更危险。

### 我把错误归因留在了仓库里

修复后我做了一件事：**没有删掉那两次错误判断，而是写进了文档。**

```markdown
# README.md 缺陷表
| 22 | 中文输入法选词的 Enter 被当成表单提交 | 与 #24 是两条不同的缺陷；此条真实存在且已修 |
| 24 | 一次提问被渲染成两轮 | **这才是用户看到的那个缺陷**；
       我前两次误判为 #17（连点）与 #22（输入法） |
```

并在 `AI-USAGE.md` §3.11 完整记录这次连续误判，在 `GLOSSARY.md` 里把不变量命名为领域术语
「单轮单消息 (One-Turn-One-Message)」。

**理由**：如果不写，仓库里会留下**两份伪造的因果**，后来者会照着错的结论继续修。

## 5. 我做过、但方法错了的一件事

发现 YTD 口径错误后，我的**第一反应**是：

> "写一个检测器，抓住这类口径错误。"

于是我写了 `lib/reconcile.ts`——一个通用对账器（499 行，其中实际代码 278 行）：口径形态检测、恒等式检查
（`PB ÷ PE ≈ ROE`、净利率 ≈ 净利÷营收）、量纲与量级边界。

它**确实抓到了**这个 bug。真机自测：

```
宁德时代 [block] 年内递增 + 跨年骤降（年界比值 0.30）
        4 期之和 11128 亿 约为单年营收的 2.6 倍
中际旭创 [block] 年界比值 0.51 → 4 期之和 1245 亿 约为单年营收的 3.0 倍
```

**我做错的地方在顺序。**

后来我做技术调研时发现：**TTM 有一套行业标准公式**，而且"把累计值当单季相加"被明确列为常见错误：

```
TTM（累计口径，业界常用）= 最近完整财年 + 本期 YTD − 上年同期 YTD
```

> "the common mistake that people make. **They don't use the year to date**...
> That's incorrect." —— Training NYC, *TTM Calculation*

如果我的第一步是**去查这个指标的标准算法**，那么：

- 正确修法是几行（改差分逻辑），不是 499 行检测器
- 而且根本不会写出错误的 `sumTTM`

**我写了一个检测器，去抓一个查一次标准公式就能避免的错误。**
更糟的是：我还在潜意识里把它当成了一次"原创设计"。

**这条纪律我改掉了**：

> 遇到一个数值错误，先问"**这个指标有没有标准算法**"，再问"要不要写检测器"。
> 检测器是兜底断言，不是正确性的主要来源。

（诚实标注：截至写作时，`sumTTM` **仍未修复**。我只加了能拦住它的检测器，
没有改口径计算本身——因为改口径会改变产品行为，需要先定口径。这属于**已知未修复项**。）

## 6. 项目最后被我自己否掉了

24 小时交付后，我继续做了技术调研和定位分析。结论是：

**作为产品，这个项目没有存在必要。**

| 我原本以为的护城河 | 调研结论 |
|---|---|
| "引用可追溯" | 已是成熟领域（citation-grounded / attribution verification），且学界已越过"引用是否存在"到"引用是否**支持**该论断"。我的实现是最弱形态 |
| "确定性算账" | 正确做法是标准公式 + 工具调用（见 §5）。我做的是被明确列为"常见错误"的那个 |
| "fail-closed 拦截" | 是个已有名字的配置项，不是发明 |
| 产品竞争力 | 同类开源项目 OpenBB 有 74k star；有一个同技术栈（TypeScript + Next.js + DeepSeek）、同形态的项目只有 1 star |

我还否掉了自己的另外三个候选定位（web 应用 / skill / 契约库），因为每一个都能找到更成熟的先例。

**这部分对招聘方的意义**：我不认为"做出一个能跑的东西"是能力的证明。
**能判断出"这个东西不该存在"，并说清依据，是更稀缺的能力。**

## 7. 可迁移的三条结论

### ① 你的验证能力边界 = 你能产生反馈信号的范围

测试、契约、评审、监控——它们全都是**信号处理器**，前提是**有信号**。
一旦失效是静默的（不报错、不改退出码、不影响断言），整套体系对它透明。

**扩展边界的唯一办法不是加更多测试，而是往"不报错"的地方装新型传感器。**

这个项目里，有效的三种新型传感器是：

| 传感器 | 抓到了什么 | 为什么自动化测试做不到 |
|---|---|---|
| 真实浏览器/CDP | IME 组词、真实事件顺序 | jsdom 的合成事件不触发原生表单提交 |
| 真实数据（而非 fixture） | YTD 口径错误 | fixture 是我按自己的理解造的，它复现的是我的错误理解 |
| **人的眼睛** | "只有文字没有 UI"、"数字不对" | 它不是断言，是**模式识别** |

### ② fixture 是"我的理解"，不是"世界的真相"

最讽刺的一点：那个 stale fixture（含旧硬编码 `taxRate: 15`），**是用我自己的错误理解生成的**。
用它做回归测试，等于用错误验证错误。

**真机数据不是可选项，是唯一的 ground truth。**

### ③ AI 的效率边界，与人的判断边界，是同一条线

AI 在这个项目里承担了绝大部分实现工作，并产出了不错的缺陷发现率（20/24）。
但三件事它**结构性地做不到**：

1. **发现"不报错的失效"** —— 它的所有工具都在监听报错
2. **给出审美与产品感判断** —— "太丑了"、"不像一个对话产品"，这不是断言能表达的
3. **在正确的地方收手** —— 它倾向于继续实现；喊停、承认方向错了，需要人来判断

## 8. 收尾

这个项目最终交付了：6,909 行源码、7,934 行测试、24 条缺陷记录、4 个真实数据源接入，
以及一份 21MB 的完整人机协作会话记录。

而它最严重的那条缺陷——**错 3 倍、盖着"TTM"的章、穿过全部关卡的宁德时代数字**——
不在那 24 条记录里。

因为它是**被坐在电脑前的人，看一眼发现的**。
